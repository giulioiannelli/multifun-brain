# Results tracking

## Output directory convention

For each dataset, results go under:

```
data/correlation_matrices_results/<dataset>/
├── results.pkl            # pickled list of PipelineResult
├── summary.csv            # one-row-per-(label,filter) summary table
├── config.json            # snapshot of the PipelineConfig used (always include)
├── manifest.csv           # input file list with metadata (for batches)
├── failed_matrices.json   # per-matrix errors that did not abort the run
├── per_matrix/            # optional per-matrix dumps (heatmaps, dendrograms, ...)
└── figures/               # optional figures generated by scripts/notebooks
```

The April batch lives at `data/correlation_matrices_results/april/{global,bands,patients}/`.

## Rules

- **Always snapshot the config.** Either write `config.json` next to
  `results.pkl`, or rely on `PipelineResult.config` being inside the
  pickle (it is, by construction). For human-readability, also dump
  `config.json` so a reviewer doesn't need to unpickle.
- **Don't commit results.** `data/*` is gitignored — keep it that way.
  Outputs are reproducible from inputs + config.
- **Failed matrices go to `failed_matrices.json`**, not silently dropped.

## Dated reports

When an analysis concludes (a meaningful finding, a parameter sweep,
contrast comparison), write a Markdown report under `.claude/reports/`
with the filename pattern:

```
YYYY-MM-DD_<key-terms-kebab-case>.md
```

Examples:

- `2026-05-20_repo-inventory.md`
- `2026-05-22_april-global-lrg.md`
- `2026-06-01_co2-vs-rest-multiscale.md`

Report structure (suggested):

1. **Context** — what data, what config, what question.
2. **Method** — pointers to scripts / notebooks used.
3. **Findings** — concise numerical results.
4. **Next steps** — open questions / follow-ups.

Reports are **append-only**: once written and dated, treat as historical
record. If a later analysis supersedes a finding, write a new report
that links back rather than editing the original.

## Recording in `history/`

`.claude/history/` chronicles *code-architecture and best-practice*
evolution. Use it when a refactor, convention change, or new tooling
choice happens — not for every analysis output (those go in `reports/`).
